# Синхронна та асинхронна комунікація (Лабораторна робота №4)

## 1. Що змінилося порівняно з лабораторною 3?
У Лабораторній роботі №3 ми розділили відповідальності на рівні Application за допомогою патерну CQS. Проте логіка залишалася лінійною: Command Handler виконував усі дії послідовно. 
У цій роботі ми навчилися обробляти побічні ефекти, які не належать до основного домену. Ми виділили допоміжні операції та реалізували комунікацію з ними як синхронним, так і асинхронним (через події) шляхом.

## 2. Які побічні операції ви виділили і чому?
Для дослідження було обрано операцію **відправки вітального email після реєстрації користувача**. 
Ця операція є ідеальним кандидатом на побічну, оскільки:
* Вона не є критичною для завершення самої транзакції реєстрації (навіть якщо лист не відправиться, користувач має бути створений).
* Вона часто залежить від зовнішніх повільних сервісів (мережеві затримки), що негативно впливає на час відповіді API.

## 3. Порівняння синхронного та асинхронного підходів

На основі проведених експериментів були зафіксовані наступні результати:

| Критерій | Синхронна комунікація | Асинхронна комунікація (Event Bus) |
| :--- | :--- | :--- |
| **Час відповіді API** | ~2600 мс (каскадна латентність: час збереження в БД + 2 сек очікування імітації email). | **~450 мс.** Основна операція завершується одразу, побічна виконується у фоні. |
| **Поведінка при збоях** | Якщо сервіс нотифікацій падає, це затримує або перериває основний потік (якщо не перехопити помилку). | Збій при відправці email ніяк не впливає на реєстрацію. Користувач гарантовано зберігається. |
| **Зв'язаність (Coupling)** | **Висока**. `RegisterUserCommandHandler` безпосередньо залежить від `NotificationService` і знає його інтерфейс. | **Низька**. Handler знає лише про `EventBus` та подію. Він не знає, хто підписаний на цю подію. |
| **Складність реалізації** | Низька. Простий виклик методу, лінійний потік, легко відлагоджувати. | Вища. Потребує написання інфраструктури (Event Bus), створення DTO подій. Відлагодження складніше через розрив call stack. |

## 4. Який підхід ви б обрали для production-системи і чому?
Для production-системи найкращим є **гібридний підхід**. 
* Основні транзакційні дії (перевірка унікальності email, збереження користувача в БД) мають виконуватися **синхронно**.
* Усі побічні дії (аналітика, розсилка листів) мають виконуватися **асинхронно** через публікацію Integration Events (наприклад, `UserRegisteredEvent`). 
Це забезпечує швидку відповідь клієнту і відкладену консистентність для допоміжних підсистем.

## 5. Що станеться, якщо одна й та сама подія буде доставлена двічі? Чи ідемпотентні ваші обробники?
У поточній простій in-process реалізації дублювання подій малоймовірне. Проте, якби ми використовували зовнішній Message Broker (RabbitMQ), подія могла б прийти двічі через збої мережі (at-least-once delivery). 
Якщо обробник не є **ідемпотентним**, користувач отримає два вітальних листи.

**Рішення:** Щоб цього уникнути, обробник подій (`NotificationService`) повинен перевіряти унікальний ідентифікатор події (Event ID) у базі даних (наприклад, таблиця `processed_events`). Якщо подія з таким ID вже оброблялася, вона просто ігнорується.
