# Модульний моноліт (Лабораторна робота №5)

## 1. Як ви визначили межі контекстів? Які альтернативи розглядали?
Для переходу до модульного моноліту систему було розділено на два обмежених контексти: **Core** (Основна бізнес-логіка) та **Analytics** (Збір статистики).
Цей поділ є логічним, оскільки ці модулі мають різні причини для змін, різні моделі даних та різні швидкості розвитку. Наприклад, сутність "Користувач" у Core містить конфіденційні дані (паролі), тоді як в Analytics користувач - це лише метрика з ID та email Розглядалася альтернатива винесення нотифікацій в окремий модуль, але Аналітика краще демонструє патерн ACL (трансляцію моделей).

## 2. Як ACL захищає модулі від змін в інших модулях?
ACL захищає модуль Аналітики від каскадних змін у Core-модулі. Ми створили транслятор (`EventTranslator`), який перехоплює зовнішню подію (`UserRegisteredEvent`) і перетворює її на внутрішню модель аналітики (`RegistrationMetric`). Якщо команда Core вирішить перейменувати поле `email` на `contactEmail` або змінити структуру події, нам доведеться оновити лише один файл-транслятор в ACL. Внутрішня бізнес-логіка Аналітики залишиться недоторканою.

## 3. Де у системі strong consistency, а де eventual consistency? Чому це прийнятно?
* **Strong Consistency (Строга консистентність):** Використовується **всередині** модуля Core. Наприклад, при перевірці унікальності email та записі користувача в базу даних усе відбувається в межах однієї транзакції. Це критично важливо, щоб уникнути створення дублікатів.
* **Eventual Consistency (Узгодженість у кінцевому підсумку):** Використовується **між** модулями (Core та Analytics). Після реєстрації Core публікує подію, а Аналітика записує метрику з мілісекундною затримкою. Це абсолютно прийнятно для бізнесу, оскільки затримка оновлення графіків на кілька секунд ніяк не впливає на здатність користувача увійти в систему.

## 4. Що зміниться, якщо потрібно буде виділити один з модулів у окремий сервіс?
Якщо навантаження на модуль Аналітики зросте настільки, що його доведеться виділити в окремий мікросервіс, наша архітектура вже до цього готова. 
Що зміниться:
* Замість in-process `EventBus` доведеться використати зовнішній Message Broker (наприклад, RabbitMQ або Kafka).
* Бізнес-логіка, моделі та ACL залишаться практично без змін, оскільки межі контекстів (Bounded Contexts) вже чітко проведені на рівні коду.

## Ретроспектива курсу

**Еволюція архітектури:**
Протягом курсу проєкт пройшов шлях від простого "спагеті-коду" до Enterprise-рішення:
1. **Lab 2:** Впровадження Чистої Архітектури (Clean Architecture) ізолювало доменну логіку від інфраструктури (бази даних, HTTP).
2. **Lab 3:** Застосування патерну CQS розділило операції читання та запису, зробивши контролери тонкими, а Use Cases перетворивши на спеціалізовані Handlers.
3. **Lab 4:** Перехід до Integration Events вирішив проблему "каскадної латентності", дозволивши виконувати побічні операції (як-от нотифікації) асинхронно у фоні.
4. **Lab 5:** Модульний моноліт провів жорсткі межі між бізнес-областями, запровадив ACL та Eventual Consistency.

**Найцінніші рішення:**
Найкориснішим архітектурним рішенням стало використання **Integration Events**. Відв'язування побічних ефектів від основного потоку виконання радикально зменшило час відповіді API та розв'язало руки для додавання нових фіч (наприклад, аналітики) без модифікації існуючого коду (дотримання Open/Closed Principle).

**Що було б зроблено інакше:**
Знаючи кінцевий результат, логічніше було б одразу структурувати папки за фічами/доменами (Feature-sliced design), а не за технічними шарами (Controllers, Services, Models). Це значно спростило б фінальний перехід до модульного моноліту.

**Trade-offs (Компроміси):**
Головний компроміс - це жертвування **простотою заради гнучкості та ізоляції**. Для того, щоб просто зареєструвати користувача і записати лог, нам довелося створити десятки файлів (DTO, Handlers, Events, Translators, Repositories). Boilerplate коду стало значно більше. Однак цей "податок на архітектуру" повністю окупається, коли система зростає, оскільки ризик зламати щось критичне при додаванні нового функціоналу зводиться до нуля.
