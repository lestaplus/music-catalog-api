# Порівняльний аналіз архітектури (Лабораторна робота №3)

## 1. Що змінилося в структурі проєкту порівняно з лабораторною 2?
У попередній лабораторній роботі шар `Application` був представлений загальними `Use Cases` (наприклад, `CreateArtistUseCase`). У цій роботі ми впровадили патерн **CQS (Command-Query Separation)**. 
Папку `use-cases` було видалено, а натомість створено дві нові:
1. `commands/` - містить DTO-команди та `CommandHandlers` для операцій зміни стану (POST, DELETE).
2. `queries/` - містить DTO-запити та `QueryHandlers` для операцій читання (GET).

Контролери стали максимально "тонкими": вони відповідають лише за мапінг HTTP-запиту в Command або Query та делегування виклику відповідному обробнику.

## 2. Переваги CQS: чим допомогло розділення?
* **Зрозумілість коду:** Тепер за назвою файлу одразу видно, що він робить. Якщо це `Command`, він точно щось змінить у базі. Якщо `Query` - він безпечний і нічого не зламає.
* **Швидкість:** Запити на читання (Queries) тепер можуть ходити в базу даних напряму. Вони більше не проходять через складні перевірки доменної моделі, що робить отримання даних набагато швидшим.

## 3. Недоліки CQS: що ускладнилося?
* **Забагато файлів:** Це головний мінус. Навіть для найпростішої дії, як-от видалення артиста, тепер треба створювати два окремі файли (DTO команди та її Handler). Через це структура папок швидко розростається.

## 4. Чим підхід з Command / Query Handler відрізняється від Service?
Класичний `Service` (наприклад, `TrackService`) зазвичай містить багато методів (`create`, `delete`, `getAll`) і має багато залежностей (декілька репозиторіїв, сервісів).
Натомість кожен `Handler` - це маленький клас із рівно одним публічним методом `execute`. Він отримує в конструктор **тільки ті залежності**, які необхідні для цієї конкретної операції.

## 5. Як CQS впливає на розширюваність?
Вплив виключно позитивний (відповідає Open/Closed Principle). Щоб додати нову фічу (наприклад, "Оновити рік артиста"), нам не потрібно модифікувати існуючий "великий" сервіс і ризикувати зламати іншу логіку. Ми просто створюємо два нових файли: `UpdateArtistCommand` та `UpdateArtistCommandHandler`, і підключаємо їх у контролері.

## 6. Чи відрізняється структура даних, яку повертає Query, від доменної моделі? Чому це важливо?
Так, відрізняється. `Query` повертає **Read Model (DTO)**, оптимізовану під потреби клієнта, минаючи домен. 
Наприклад, при отриманні списку треків (`GetAllTracksQueryHandler`), замість того щоб повертати `TrackDomainModel` (яка містить лише `artistId`), ми робимо JOIN на рівні БД і повертаємо плоский об'єкт `{ id, title, duration, artistName }`. 
Це важливо, оскільки клієнту (наприклад, UI) потрібне саме ім'я артиста для відображення, а не його ідентифікатор. Це звільняє доменну модель від обов'язку задовольняти специфічні вимоги UI.
