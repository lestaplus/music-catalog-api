# Порівняльний аналіз архітектури (Лабораторна робота №2)

## 1. Що змінилося порівняно з Лабораторною роботою №1?
У першій лабораторній роботі проєкт був побудований за принципом, де вся логіка (від валідації до запитів у БД) знаходилася безпосередньо в контролерах. Це призводило до жорсткої зв'язності коду, дублювання та неможливості незалежного тестування.

У цій роботі проведено рефакторинг та впроваджено **Чисту Архітектуру (Clean Architecture)**, яка розділила проєкт на 4 незалежні шари:
1. **Domain (Домен):** Ядро системи. Містить бізнес-правила (`Artist`, `Track`, `User`) та Інтерфейси репозиторіїв. Не знає про існування баз даних чи фреймворків.
2. **Application (Застосунок):** Містить `Use Cases` (наприклад, `CreateTrackUseCase`). Оркеструє потоки даних між Доменом та Інфраструктурою.
3. **Infrastructure (Інфраструктура):** Реалізує роботу із зовнішніми інструментами (Prisma ORM, бази даних, генерація JWT-токенів). Містить мапери (Mappers) для перетворення структур даних.
4. **Presentation (Презентація):** HTTP-рівень (Express роутери та контролери). Відповідає лише за прийом DTO та повернення відповідей.

## 2. Чому було обрано "Rich Domain Model"?
У першій роботі моделі були анемічними (Anemic Domain Model) — вони виступали лише структурами даних, а логіка перевірки була розкидана по контролерах. 

Ми впровадили **Rich Domain Model (Багату Доменну Модель)**, оскільки вона інкапсулює поведінку та стан разом. 
* **Інваріанти:** Кожна сутність (`Track`, `User`, `Artist`) містить метод `validate()`, який викликається безпосередньо в конструкторі. 
* **Перевага:** Неможливо створити невалідний об'єкт у пам'яті програми. Наприклад, об'єкт `Track` миттєво згенерує `DomainError`, якщо його тривалість $\le$ 0. База даних (Prisma) надійно захищена від "брудних" даних ще до початку формування SQL-запиту.

## 3. Переваги та недоліки нової архітектури

### Переваги:
* **Ізоляція та Тестованість:** Завдяки впровадженню залежностей (Dependency Injection) ми можемо легко писати Unit-тести для Домену та Application-шару, підміняючи реальну базу даних моками.
* **Безпека (Whitelisting):** У контролерах реалізовано суворе обмеження DTO. Це захищає систему від вразливостей.
* **Консистентність:** Використання `DomainError` дозволило створити єдиний центр обробки помилок у контролерах.

### Недоліки:
* **Ускладнення навігації:** Кількість файлів зросла в кілька разів. Щоб прослідкувати один HTTP-запит, тепер потрібно пройти через маршрут, контролер, use case, фабрику та репозиторій.
* **Оверхед на мапінг:** Дані доводиться перетворювати кілька разів (DTO $\rightarrow$ Domain Model $\rightarrow$ Persistence Model), що вимагає написання додаткових класів (`UserMapper`, `TrackMapper`). Для дуже простих CRUD-запитів така архітектура може здаватися надлишковою.

## 4. Наскільки простіше замінити базу даних?
Заміна бази даних (наприклад, перехід з PostgreSQL на MongoDB або заміна Prisma ORM на TypeORM) тепер є **максимально простою та ізольованою задачею**. 

Це досягнуто завдяки патерну **Dependency Inversion (Інверсія залежностей)**:
1. Бізнес-логіка (`Use Cases`) залежить не від Prisma, а від абстрактних контрактів (наприклад, `IUserRepository`).
2. Якщо ми змінимо БД, нам не доведеться змінювати жодного рядка коду в `Domain` чи `Application`. 
3. Достатньо створити новий клас (наприклад, `MongoUserRepository`), який реалізує інтерфейс `IUserRepository`, переписати відповідний Mapper і підставити новий репозиторій у `Router` під час ініціалізації залежностей.

## Висновок
Рефакторинг дозволив перетворити сильно зв'язний код-лапшу на масштабовану, безпечну та стійку до змін систему. Незважаючи на збільшення об'єму коду та складності навігації, отримана архітектура є необхідним стандартом для розробки великих комерційних проєктів.
